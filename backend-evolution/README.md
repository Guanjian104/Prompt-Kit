- 先只读分析现有代码，建立系统现状和依赖关系。
- 对照新页面需求，形成新旧功能与接口差异清单。
- 制定接口兼容、服务边界和数据迁移方案。
- 等你确认方案后，再分模块实施。
- 每个阶段执行测试、检查兼容性，并汇报实际变更。

### 一、推荐的 Cursor 项目配置

建议在仓库中建立一个专门的改造 Skill，不把所有规则塞进全局提示词。

```txt
your-project/
├── .cursor/
│   └── skills/
│       └── backend-evolution/
│           └── SKILL.md
├── docs/
│   └── backend-evolution/
│       ├── 01-current-state.md
│       ├── 02-requirement-mapping.md
│       ├── 03-api-compatibility.md
│       ├── 04-technical-design.md
│       ├── 05-implementation-plan.md
│       └── 06-test-and-release.md
├── services/
│   ├── service-a/
│   ├── service-b/
│   └── service-c/
└── ...
```

这里有两个关键设计：

1. `.cursor/skills/backend-evolution/SKILL.md` 定义 Agent 在整个项目改造过程中必须遵循的工作方法。
2. `docs/backend-evolution/` 保存每阶段的分析和决策，避免 Agent 在多轮对话中遗忘前面的结论，或者在改代码时擅自改变已经确定的方案。

如果你希望每次打开项目时都自动遵循某些规则，可以再配置项目级 Cursor Rules；但改造流程本身适合放在 Skill 中，按任务调用。

### 四、再加一条非常重要的规则：不要让 Agent 把“计划”变成“授权”

建议在每次执行前都保留明确的阶段边界：

| 阶段     | Agent 可以做什么     | 是否允许修改业务代码     |
| -------- | -------------------- | ------------------------ |
| 现状调查 | 阅读代码、分析依赖   | 否                       |
| 需求映射 | 对照页面和接口       | 否                       |
| 技术设计 | 制定方案、评估风险   | 否                       |
| 实施计划 | 拆分任务、定义验收   | 否                       |
| 分批实施 | 按批准任务修改       | 是                       |
| 最终验证 | 测试、检查、整理报告 | 原则上否，发现问题先报告 |

即使你已经批准某个模块的改造，也不代表 Agent 可以顺便重构所有相关服务。跨越原定范围的修改，应当重新评估并取得确认。

### 五、我建议再加一个小型任务跟踪文件

除了 Skill 和阶段文档，可以增加 `docs/backend-evolution/STATUS.md`：

[STATUS.md](./STATUS.md)

每次 Agent 完成一批任务后更新这个文件。这样即使换了会话、上下文压缩，或者让另一个 Agent 接手，也能从明确的工程状态继续，而不必重新猜测之前做过什么。

### 六、最后给你一个实际建议

对于你的项目，我建议先做一个小范围试点，不要一开始就扫描、规划和重构所有微服务。

选择一个具有代表性的业务模块，最好同时包含：

- 一个已有查询接口。
- 一个需要调整的接口契约。
- 一个存在业务状态变化的操作。
- 至少一个旧客户端仍然依赖的接口。

先用上面的 Skill 完成分析和方案，再实施这一条完整业务链路。验证通过后，把过程中形成的接口约定、测试模式和代码边界固化到 Skill 中，再推广到其他模块。
