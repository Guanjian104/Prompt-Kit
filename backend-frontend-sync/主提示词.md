## 3. 第一阶段：分析，不修改业务代码

先分析前端项目中的实际页面、路由、API 调用、请求参数、响应字段、认证和错误处理方式。

然后分析后端项目中对应的接口、DTO、服务、数据访问、权限、事务和测试。

请特别注意：

- 以实际前端调用代码为主要线索，而不是只看接口名称或类型声明。
- 不要把 Mock 数据或前端类型定义直接当作后端真实契约。
- 优先查找已有后端能力及其调用方，判断能否复用。
- 标明已确认事实、合理推测和需要人工确认的事项。
- 不要仅因前端和后端处于同一工作区就假设它们共用 Git 仓库或构建流程。

## 4. 输出分析结果

请整理以下内容：

1. 页面主要操作和业务流程。
2. 前端 API 调用清单：URL、HTTP 方法、参数来源、请求结构、响应使用方式。
3. 前端 API 与后端现有接口的映射关系。
4. 每项接口差异及分类：直接复用、轻量适配、既有业务扩展、新增能力、高风险变更。
5. 需要修改的后端文件及原因。
6. 兼容旧接口和旧业务的方案。
7. 测试、联调及回归计划。
8. 尚不明确的问题和需要确认的风险。

可以创建或更新以下分析文档，但不要修改业务实现：

- `docs/backend-evolution/frontend-api-inventory.md`
- `docs/backend-evolution/api-mapping.md`

如已有文档，先检查内容，增量更新，不要无理由覆盖。

完成分析后，先汇报实施方案。
