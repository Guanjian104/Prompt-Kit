> Skill 通常只需要配置一次；主提示词每次新任务使用；分阶段提示词按需使用。 不是每个地方都必须手动填写。如果暂时不知道某项信息，可以明确写“请从代码中分析”，让 Agent 去查证。

### 一、先准备一份通用的“项目资料”

后面所有提示词里的项目路径、页面名称、接口名称等，都可以从这份资料中取值。不必每次重新想一遍。

以下是虚构示例，路径和接口仅用于说明填写方法。

| 项目资料     | 示例填写内容                                | 去哪里确认           |
| ------------ | ------------------------------------------- | -------------------- |
| 前端项目路径 | `./admin-web`                               | Cursor 工作区目录    |
| 后端项目路径 | `./device-server`                           | Cursor 工作区目录    |
| 前端技术栈   | Vue 3 + TypeScript + Vite                   | `package.json`       |
| 后端技术栈   | Java + Spring Boot + MyBatis                | `pom.xml`、源码      |
| 页面名称     | 设备管理页面                                | 页面路由、产品需求   |
| 业务操作     | 查询设备、查看详情、启停设备                | 页面按钮和交互       |
| 现有接口     | `GET /api/devices`、`GET /api/devices/{id}` | 后端路由、Controller |
| 验收标准     | 列表可展示、详情可打开、启停结果正确        | 页面实际需求         |
| 特别约束     | 不修改前端，不破坏旧接口                    | 项目适配要求         |

如果你不知道前端或后端使用什么技术栈，可以不填写，让 Agent 先识别。不要为了填满提示词而猜测项目情况。

### 二、Skill 中的填写示例

Skill 本身基本不需要反复填写。你只需在首次配置时检查以下部分。

1. `name`：Skill 名称

示例：`backend-frontend-sync`

这是固定标识，后续提示词中引用时要保持一致。

2. `description`：用途说明

示例：

```
适用于前后端分属不同项目、Cursor 同时打开两个项目，根据新前端页面适配现有后端接口，并完成联调和回归测试。
```

这段描述帮助 Cursor 判断该 Skill 适用于什么任务。

3. 项目路径

如果你在 Skill 中希望固定项目路径，可以写：

- 前端：`admin-web/`
- 后端：`device-server/`

但如果项目目录可能变化，更推荐在主提示词里填写，不要把临时路径固化到 Skill。

4. 文档输出路径

示例：

- `docs/backend-evolution/frontend-api-inventory.md`
- `docs/backend-evolution/api-mapping.md`
- `docs/backend-evolution/integration-notes.md`

这些是建议的文档位置。如果你的项目已有 `doc/`、`docs/architecture/` 等目录，应优先沿用现有规范。

### 三、主提示词中每个填写位置怎么填

主提示词中需要填写的地方主要有以下几项。

1. 前端项目路径

占位符：`<填写前端项目目录或名称>`

示例：`./admin-web`

如果 Cursor 已经打开两个项目，也可以填写工作区中实际显示的目录名。

2. 后端项目路径

占位符：`<填写后端项目目录或名称>`

示例：`./device-server`

应指向实际后端项目根目录，而不是某个 Controller 文件夹。

3. 页面或功能名称

占位符：`<填写>`

示例：`设备管理页面，包括设备列表、设备详情和设备启停操作。`

应描述用户能看到或操作的功能，而不是只写“新增页面”。

4. 业务操作及预期结果

占位符：`<填写>`

示例：

```
用户进入设备管理页面后，可以分页查询设备，按设备名称和运行状态筛选；点击设备可查看详情；有权限的用户可以执行启用和停用操作，页面显示操作结果。
```

尽量写清楚用户操作、输入条件和期望结果。

5. 特别约束

占位符：`<填写，没有则写无>`

示例：

```
前端项目只读；尽量复用已有设备服务；不改变旧接口的请求和响应格式；不擅自修改数据库结构、权限规则及部署配置。
```

如果没有额外限制，可以写“无额外约束，遵循 Skill 中的默认规则”。

6. 验收标准

占位符：`<填写；如果暂不明确，请根据代码梳理并列出待确认项>`

示例：

```
设备列表能够正确展示分页数据；筛选条件生效；详情数据与列表中的设备一致；启停操作成功后状态正确更新；无权限操作会被拒绝；现有设备相关接口的回归测试通过。实际无法验证的项目需单独标明。
```

验收标准应尽量可验证，避免只写“功能正常”。

### 四、分阶段提示词中每个填写位置怎么填

#### 阶段 1：分析前端和后端

这个阶段一般只需要填写两个路径。业务需求也可以提供，但即使你暂时不清楚完整接口，Agent 也应先从代码中分析。

| 占位符           | 示例              | 说明           |
| ---------------- | ----------------- | -------------- |
| `<前端项目路径>` | `./admin-web`     | 前端项目根目录 |
| `<后端项目路径>` | `./device-server` | 后端项目根目录 |

建议第一次先使用下面这个已填写的完整示例：

```markdown
请执行 backend-frontend-sync Skill 的阶段 A 和阶段 B 前置分析。

当前 Cursor 工作区包含两个项目：

- 前端：`./admin-web`
- 后端：`./device-server`

本阶段只做分析，不修改前端或后端业务代码。

请检查两个项目的根目录、技术栈、Git 仓库边界和工作区状态。分析前端实际的设备管理页面、路由、组件和 API 调用，追踪查询设备列表、查看详情、启用设备和停用设备等操作对应的请求。

然后在后端项目中查找相关接口、DTO、服务方法、数据访问逻辑、权限校验和测试。

请建立以下调用映射：

页面操作 → 前端 API → 后端接口 → 服务逻辑 → 数据或外部依赖 → 前端使用的响应字段。

重点识别请求方法、URL、分页和筛选参数、请求及响应字段、错误处理、认证和权限要求，以及现有接口是否能够复用。

请生成或增量更新：

- `docs/backend-evolution/frontend-api-inventory.md`
- `docs/backend-evolution/api-mapping.md`

输出接口映射表、差异分类、可复用能力、建议修改的后端文件、兼容性风险和测试计划。区分已确认事实、推测和待确认事项。

前端项目只读，不修改业务代码，不开始实施。分析完成后停止并等待下一步指示。

如果实际目录或页面名称与示例不同，请根据工作区中的真实项目结构识别，不要因为示例不匹配而假设相关代码不存在。
```

#### 阶段 2：实施后端适配

这一阶段填写的内容最重要，因为它直接决定 Agent 的修改范围。

| 占位符             | 示例                                                         |
| ------------------ | ------------------------------------------------------------ |
| `<页面或业务流程>` | 设备管理页面的列表查询、详情展示和启停操作                   |
| `<需要适配的接口>` | `GET /api/devices`、`GET /api/devices/{id}`、`POST /api/devices/{id}/status`（示例接口，需先核实） |
| `<已确认的差异>`   | 前端需要分页和状态筛选；现有查询接口可能不支持状态筛选；详情响应字段与前端使用字段存在差异 |
| `<验收标准>`       | 列表、筛选、详情、启停均符合前端实际调用要求；旧接口回归测试通过 |

这里要特别注意：接口路径和差异不能因为示例中出现了就直接照搬。 应当先从分析报告中确认实际路径与字段。如果 Agent 还没找到，就写“根据前一阶段分析结果填写，不得假定接口存在”。

以下是完整填写示例：

```markdown
请根据已确认的接口清单和前后端接口映射，执行 backend-frontend-sync Skill 的阶段 C。

## 本次实施范围

- 页面或业务流程：设备管理页面的列表查询、详情展示和启停操作。
- 需要适配的接口：以前一阶段确认的实际后端接口为准，优先检查设备列表查询、设备详情查询和设备状态变更相关接口。
- 已确认的差异：前端需要分页、设备名称筛选和运行状态筛选；需要核实后端是否已支持这些条件；前端展示的详情字段需要与后端实际响应映射；启停操作需要符合现有设备状态规则。
- 验收标准：列表数据、分页和筛选结果正确；详情字段符合前端使用方式；启停操作遵循既有业务规则；权限校验保持有效；已有接口和关键业务回归测试通过。

## 修改约束

只修改后端项目中的必要文件，前端项目保持只读。开始前检查工作区状态，保留已有修改。

优先复用现有设备查询服务、设备详情服务和状态控制逻辑。优先采用 DTO 转换、参数映射和响应适配等最小必要改动。

不得擅自修改数据库结构、核心业务规则、权限、事务、部署配置或公共接口契约。如果发现必须修改这些内容，先解释原因、影响和替代方案，等待确认。

## 测试要求

为新增或调整的行为补充必要测试，运行项目已有且适用的测试或构建命令。具备测试环境时，验证真实请求和响应。不得声称执行过实际未运行的测试。

完成后汇报修改文件、接口变化、现有能力复用情况、测试命令与真实结果、联调状态以及未解决的风险。

本次任务只处理上述范围，不要顺带重构其他业务。
```

这个示例采用了“业务范围明确、具体接口根据实际分析结果确认”的写法。如果你已经知道精确的接口路径，可以把路径直接填进去；如果不知道，就不要猜。

#### 阶段 3：联调排错

这个阶段需要填写实际发生的问题。如果信息不完整，可以先填已知信息，让 Agent 从代码、日志或测试中继续调查。

| 占位符                         | 示例                                                         |
| ------------------------------ | ------------------------------------------------------------ |
| <页面或业务流程>               | 设备管理页面的设备列表查询                                   |
| <预期行为>                     | 进入页面后显示第一页设备数据                                 |
| <实际行为>                     | 页面显示空列表，但后端日志显示查询接口已被调用               |
| <请求 URL 和 HTTP 方法>        | `GET /api/devices?page=1&pageSize=20`（示例，需以真实请求为准） |
| <请求参数或脱敏后的请求体>     | `page=1&pageSize=20&status=online`（示例）                   |
| <实际响应状态码及脱敏后的响应> | `200`，但返回的 `data` 为空数组（示例）                      |
| <后端日志或异常堆栈>           | 查询日志显示未应用状态筛选条件，或 SQL 参数与预期不一致（示例，需核实） |
| <复现步骤>                     | 打开设备管理页面，选择“运行中”，点击查询                     |

下面是已填写的示例：

```markdown
请执行 backend-frontend-sync Skill 的阶段 D，排查设备管理页面的列表查询问题。

## 问题信息

- 页面或业务流程：设备管理页面的设备列表查询。
- 预期行为：页面打开后显示设备列表；选择运行状态筛选条件后，列表只展示符合条件的设备。
- 实际行为：页面发起查询后显示空列表，实际原因尚未确认。
- 请求 URL 和 HTTP 方法：请从前端实际请求或浏览器网络记录中确认，不要直接采用示例路径。
- 请求参数或脱敏后的请求体：请检查分页参数、设备名称筛选参数和状态筛选参数的实际名称、类型和值。
- 实际响应状态码及脱敏后的响应：目前尚未确认，请检查真实响应的状态码、响应结构和数据字段。
- 后端日志或异常堆栈：目前尚未提供，请检查已有日志、查询参数和相关异常。
- 复现步骤：打开设备管理页面，选择“运行中”状态，执行查询，观察页面结果及对应的网络请求。

## 排查要求

先只读检查前端请求及响应处理逻辑，再沿后端接口入口、参数解析、权限校验、服务层、数据库查询和响应序列化的链路定位问题。

判断问题属于前后端契约不一致、参数解析、筛选逻辑、数据权限、数据库数据、响应映射还是环境问题。

在有足够证据后，提出根因并对后端进行最小修复。前端项目保持只读，不得通过关闭权限校验、伪造成功结果或吞掉异常来绕过问题。

修复后运行相关测试，并在条件允许时复现原始请求进行验证。最终说明根因证据、修改文件、测试结果和仍未验证的环节。

如果缺少必要证据，不要盲目修改代码，请列出下一步需要的日志、请求或测试信息。
```

这个示例故意没有编造实际状态码、响应内容或 SQL 错误。你遇到真实问题时，有什么就填写什么；没有的就标记“尚未确认”。

#### 阶段 4：复杂业务变更分析

这一阶段只需要填写一个核心内容：你希望新页面实现什么业务行为。

| 占位符                                       | 示例                                                         |
| -------------------------------------------- | ------------------------------------------------------------ |
| <描述页面需求、操作流程、预期结果和已知约束> | 设备管理页面新增批量启停功能，支持选择多台设备并统一执行操作；需要核实部分成功、失败回滚、权限及状态一致性规则 |

填写示例：

```markdown
本次需求：设备管理页面新增批量启停功能。

用户可以在设备列表中选择多台设备，统一执行启用或停用操作，并在操作完成后查看每台设备的执行结果。

请执行 backend-frontend-sync Skill 的阶段 A 和阶段 B，先分析，不修改业务代码。

请追踪前端实际调用方式，检查后端现有设备控制接口、设备状态规则、权限校验、事务边界、外部设备通信和相关调用方。

重点分析以下问题：

1. 后端是否已有可复用的单设备控制能力。
2. 批量操作应串行还是并行执行，现有架构是否支持。
3. 如果部分设备成功、部分设备失败，业务上应该如何返回结果。
4. 是否需要事务、补偿机制、幂等控制或任务状态查询。
5. 操作权限如何校验，是否需要逐台检查设备权限。
6. 是否会影响现有单设备启停接口和其他页面。
7. 前端需要什么样的请求结构和结果结构。

请给出当前调用链、现有能力与需求差距、推荐方案、可选方案、影响范围、兼容策略、测试计划和待确认的业务规则。

涉及权限、事务、状态一致性、跨服务协议或数据库变更时，必须先等待我确认。本阶段只分析和制定计划，不修改业务代码。
```

### 五、实际使用时，哪些内容可以不填？

你不需要每次都把所有信息准备完整。可以按下面的规则处理：

已经知道的内容：直接填写

​	例如项目目录、页面名称、明确的业务需求、已复现的错误。

可以从代码中查到的内容：让 Agent 分析

​	例如接口路径、DTO 字段、调用链、现有服务是否能复用、项目构建命令。

涉及业务决定的内容：先列为待确认

​	例如批量操作部分失败怎么办、旧接口是否允许变更、数据迁移如何执行。不要让 Agent 擅自决定。

涉及敏感信息的内容：先脱敏

​	日志、请求体、令牌、Cookie、数据库连接信息等，不要直接粘贴密码、访问令牌或真实用户敏感数据。



**最后提醒**： 上面填写器生成的是“先分析、等待确认”的主提示词。分析结果确认之后，再使用阶段 2 提示词实施；如果实际联调出现问题，再使用阶段 3。这样能减少每次重复填写，也能避免 Cursor 在尚未摸清后端业务时就直接改代码。
