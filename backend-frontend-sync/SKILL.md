# Backend Frontend Sync

## 1. 核心目标

前端团队先完成页面，后端开发者将前端项目和现有后端项目同时放入 Cursor 工作区。

Agent 需要以实际前端代码为需求依据，以现有后端代码和业务规则为实现依据，快速识别接口差异，尽可能复用已有业务能力，以最小必要改动完成后端适配、测试和联调。

核心原则：

- 前端先行，后端适配。
- 前端代码默认只读，后端代码按任务范围修改。
- 先分析现状，再提出方案，获得必要确认后再实施。
- 优先复用现有接口、服务和业务逻辑。
- 兼容优先，小步修改，避免无关重构。
- 测试结果必须真实，不得声称执行过未执行的测试。

## 2. 双项目与 Git 仓库边界

开始工作前，识别：

- 前端项目根目录及技术栈。
- 后端项目根目录及技术栈。
- 两个项目是否属于独立 Git 仓库。
- 各仓库当前分支、工作区状态和已有未提交变更。
- 两个项目各自的构建、测试、运行方式（如可识别）。

不得假设两个项目共用同一套构建工具、依赖、配置或 Git 历史。

默认权限：

### 前端项目

允许：
- 阅读页面、路由、组件、状态管理和 API 调用代码。
- 阅读 API 封装、请求拦截器、类型定义、Mock 数据和相关文档。
- 根据页面操作追踪请求与响应的使用方式。

默认禁止：
- 修改、格式化、重命名或删除前端文件。
- 修改前端依赖、构建配置、环境变量或锁文件。
- 为了让后端实现更简单而擅自修改前端调用方式。

### 后端项目

允许：
- 阅读接口层、DTO、服务层、数据访问层、实体、配置和测试代码。
- 在确认的任务范围内修改后端实现。
- 按项目现有规范补充测试、必要的接口文档和适配代码。

默认禁止：
- 无关重构或大范围重命名。
- 未经确认修改核心业务规则、权限、事务、数据模型或数据库结构。
- 未经确认修改部署配置、公共基础设施或其他服务项目。
- 执行会覆盖、清理或撤销用户已有修改的危险操作。

如确实需要修改前端或其他项目，先说明必要性、涉及文件、影响和替代方案，等待确认。

## 3. 分析前端实际需求

不能只看页面截图、接口名称或类型定义。应尽可能从真实代码追踪：

1. 页面路由与业务入口。
2. 用户操作及其触发的请求。
3. API 请求封装、URL、HTTP 方法和请求参数。
4. Query、Path、Body、Header、Cookie 等参数来源。
5. 请求和响应字段、空值处理、枚举值、时间格式和分页约定。
6. 登录态、认证、权限和租户等上下文。
7. 错误码、异常提示、加载状态、重复提交和重试机制。
8. 文件上传下载、实时推送、WebSocket、SSE 等特殊通信方式。
9. 页面依赖的业务状态、状态流转和操作结果。
10. 相关 Mock 数据、前端类型、接口文档与真实调用之间的差异。

前端类型定义、Mock 数据和注释都只是证据，不等于后端真实契约。遇到不一致时，应继续核对后端代码、测试、历史实现和实际运行结果。

## 4. 分析后端现有能力

围绕前端调用逐项定位：

- Controller、Router、Handler 或同等接口入口。
- Request DTO、Response DTO、参数校验。
- Service、领域逻辑和已有业务流程。
- Repository、Mapper、ORM、数据库表及关联关系。
- 权限校验、事务、缓存、消息队列和外部服务调用。
- 异常处理、统一响应格式、日志和测试。
- 已有接口的调用方及兼容性要求。

建立明确映射：

前端页面操作 → 前端 API 调用 → 后端接口 → 服务方法 → 数据访问或外部依赖 → 前端使用的响应字段。

如果已有能力可以复用，不要重复实现同一业务规则。

## 5. 接口差异分类

将发现的问题分为：

A. 直接复用：现有接口已满足需求。

B. 轻量适配：字段映射、DTO 转换、参数默认值、枚举转换或响应格式适配。

C. 既有业务扩展：现有服务能力可复用，但需要增加受控的业务分支或参数。

D. 新增能力：后端不存在对应业务能力，需要新增接口或服务逻辑。

E. 高风险变更：涉及权限、安全、事务、数据一致性、状态机、数据库迁移、跨服务协议或可能破坏旧接口的变化。

A、B 通常可以按明确范围快速实施。C、D 需要说明设计与影响后实施。E 必须先给出分析、风险和方案，等待用户确认。

## 6. 实施规则

每次只处理明确的页面、业务流程或接口范围。

实施前明确：

- 本次目标和验收标准。
- 计划修改的后端文件。
- 可复用的现有接口和业务逻辑。
- 是否需要数据库、配置、权限或其他服务变更。
- 测试方式和联调条件。

实施时：

1. 先阅读相关代码和相邻调用链。
2. 采用最小必要改动。
3. 优先使用项目已有架构、命名、异常处理和响应规范。
4. 尽量保留旧接口、旧字段和旧业务行为。
5. 不要把仅供新页面使用的字段直接加入共享模型，除非语义和影响已经确认。
6. 不得通过关闭权限校验、放宽数据隔离或吞掉异常来解决联调问题。
7. 不得因前端传入参数就默认该参数可信。
8. 未经确认，不执行破坏性数据库迁移或数据修改。
9. 如发现需求与现有业务规则冲突，暂停相关修改并解释冲突。

## 7. 联调与测试

按可用程度逐步验证：

- 静态检查和代码格式检查。
- 编译或构建。
- 单元测试。
- 集成测试。
- 接口请求与响应验证。
- 真实前后端联调。
- 旧接口及关键业务回归。

重点检查：

- HTTP 方法、URL 和参数位置是否匹配。
- 请求字段类型、必填约束和空值语义是否一致。
- 响应结构、字段名称、枚举、时间格式和分页格式是否符合前端使用方式。
- 认证、权限和数据范围是否正确。
- 错误响应是否能被前端正确处理。
- 数据写入、状态流转、事务和重复提交行为是否正确。
- 旧页面、旧调用方和已有接口是否受到影响。

没有运行测试时，不得声称测试通过。由于缺少数据库、依赖服务、凭证或环境导致无法验证时，必须说明具体阻塞点。

## 8. 工作阶段

### 阶段 A：环境识别和需求分析

只读检查两个项目，识别仓库边界、工作区变更、页面流程、API 调用和后端现状。输出接口清单和待确认事项，不修改业务代码。

### 阶段 B：接口映射和实施计划

明确前后端接口映射、差异分类、修改文件、兼容策略、风险和测试方案。高风险事项先等待确认。

### 阶段 C：定向实现

按确认范围修改后端，优先复用现有能力，补充必要测试，不修改前端。

### 阶段 D：联调排错

根据实际请求、响应、日志和异常定位问题，沿完整调用链修复根因，避免无关修改。

### 阶段 E：交付与回归

总结修改内容、接口变化、测试结果、未解决事项、风险和后续建议。

## 9. 文档与产物

按需维护：

- docs/backend-evolution/frontend-api-inventory.md：前端 API 调用清单。
- docs/backend-evolution/api-mapping.md：前后端接口映射与差异。
- docs/backend-evolution/integration-notes.md：联调问题、原因和验证结果。

文档应与实际代码一致。不要为了生成文档而重复复制大量源码，也不要把推测标记为已确认事实。

## 10. 最终汇报格式

每次任务完成后，说明：

1. 适配的页面或业务流程。
2. 前后端接口映射结果。
3. 修改的后端文件及用途。
4. 采用的兼容方案和复用的现有能力。
5. 测试项目、执行命令及实际结果。
6. 是否完成真实接口联调。
7. 尚未解决的问题、环境限制和上线风险。
8. 是否需要人工确认或后续处理。

明确区分“代码已修改”“构建通过”“自动化测试通过”和“真实联调通过”，不得混为一谈。
