### 零、引言

这套方案针对你的实际工作流设计：**前端团队先完成页面 → 你在 Cursor 中同时打开前后端项目 → Agent 先分析前端实际需求 → 对照后端现有能力 → 快速适配 → 实际联调与回归。**

整套方案分为四部分：

1. **Skill**：长期规则，放进后端项目的 `.cursor/skills/`，以后反复使用。
2. **主提示词**：每次新页面适配任务的统一入口。
3. **分阶段提示词**：分析、实施、联调、复杂变更分析四类，按需使用。
4. **执行约定**：明确双仓库边界、修改权限、测试标准和交付格式。

默认原则是：**前端项目只读，后端项目是主要修改目标；先分析再实施，小步修改，保留旧功能，不把“代码写完”误认为“联调完成”。**

### 一、Skill

建议保存为后端项目中的：

`backend/.cursor/skills/backend-frontend-sync/SKILL.md`

如果你实际把 `.cursor` 目录放在工作区级别，也可以按自己的目录组织方式调整。Skill 的重点是长期约束 Agent 的行为，而不是绑定某个特定技术栈。

每次收到前端团队交付的新页面后，先发这个主提示词。它会要求 Agent 先摸清两个项目的情况，并生成适配计划，不直接大范围改代码。

### 四、实际使用时的推荐顺序

**准备：同时打开两个项目**

​	确认前端和后端目录、各自 Git 状态；先不要修改代码。

**第一步：发送主提示词**

​	填好页面名称、业务需求和验收标准。让 Agent 先分析并输出接口映射。

**第二步：审核分析结果**

​	重点检查接口是否找对、旧业务能否复用、是否存在权限或数据兼容风险。

**第三步：发送阶段 2 提示词**

​	指定允许修改的接口和验收标准，要求 Agent 定向修改后端。

**第四步：联调并回归**

​	遇到问题时发送阶段 3；涉及复杂业务、跨服务或数据库变更时，先发送阶段 4。

### 五、最后三个落地建议

1. **Skill 放在后端项目中。** 这样后端项目的开发规范与适配规则放在一起。注意 Skill 不会自动替代每次任务的验收要求，主提示词仍然要填写具体需求。
2. **接口清单与映射文档要持续更新。** 新页面到来时，先增量分析，而不是每次从头探索整个后端。涉及已变化的代码时，仍需重新核实。
3. **将“修改边界”和“完成标准”分开。**前端只读、后端定向修改是权限边界；构建通过、测试通过、真实联调通过则是不同的验收等级。

这套方案适合先从一个页面、几条接口开始试运行。跑通之后，再把实际有效的测试命令、项目目录约定、接口规范和常见业务规则补充进 Skill，逐渐形成你自己的后端快速适配工作流。
